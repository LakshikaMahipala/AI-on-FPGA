# Stress Detector on FPGA: Learning Prototype (v0)

> First end-to-end attempt at FPGA inference: a PyTorch model for facial stress detection, an image sent to the FPGA over UART, and a Verilog datapath that returns a prediction.

**Status:** ⚠️ Prototype. The communication path is in place (UART → image RAM → MAC datapath → UART), but the hardware does **not** yet run the trained network. It is kept to show the starting point; the full design continues in [`../fpga-ai-accelerator`](../fpga-ai-accelerator).

## What works
- PyTorch training notebook (FER2013, stressed vs not stressed): [`stress-detection.ipynb`](stress-detection.ipynb)
- UART receiver and transmitter (115200 baud, 50 MHz clock), image buffer RAM
- Building-block modules: 3×3 MAC convolution, ReLU, 2×2 max-pool, MAC fully-connected layer, argmax

## Known issues (found in code review, November 2026)
| # | Issue | Effect |
|---|---|---|
| 1 | Exported weights: 1,721 of 1,728 values in `layer0_features_0_weight.mif` are 0 (the rest are ±1) | Float weights (~0.01) were rounded to integers without a scale factor, so the conv layer outputs 0 |
| 2 | `weight_rom.v` loads a Quartus `.mif` file with `$readmemh`, which expects plain hex | The ROM does not load the intended values |
| 3 | `top.v` uses one 3×3 MAC and FC layers with `INPUT_SIZE = 1` and constant weights 1 and 2 | The trained network is not implemented; logit 1 is always 2 × logit 0 |
| 4 | `uart_rx.v` / `pixel_ram.v` use a 17-bit address for a 224×224×3 = 150,528-byte image | 2¹⁷ = 131,072, so the address overflows |
| 5 | The testbench sends 9 bytes and has no expected-value check | It cannot show pass or fail |
| 6 | `` `timescale `` was missing its backtick in the testbench | Did not compile; **fixed** |

These are normal first-prototype problems. Each one is addressed by design in the accelerator project: per-tensor scale factors, hex ROM files generated by a Python golden model, parameterised address widths, and self-checking testbenches.
